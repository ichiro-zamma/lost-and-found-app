# 設計書

落とし物管理・マッチングアプリのフロントエンド実装における、型定義・コンポーネント構成・state設計・バリデーション設計の方針をまとめたもの。個別の画面を実装する際は、本書の方針に沿って設計する。

## 1. 型定義の方針

### 1-1. 基本方針

- DBのテーブル構造に対応する型は、独自に定義せず**Prismaが自動生成する型をそのまま利用する**
- `src/generated/prisma/client` からimportして使う

```typescript
import type { LostItem, FoundItem, Category, Color, Location, Facility, User, Match } from '@/generated/prisma/client'
```

- リレーション先を含めて取得したデータの型は、Prismaの `Prisma.LostItemGetPayload<...>` を使うか、関数の戻り値から `Awaited<ReturnType<typeof ...>>` で推論する。独自にリレーション込みの型を手書きしない(スキーマ変更時に型がズレる原因になるため)

```typescript
// 例: カテゴリ・色・場所を含めて取得する関数の戻り値型
async function getLostItemsWithMaster() {
  return prisma.lostItem.findMany({
    include: { category: true, color: true, location: true },
  })
}
type LostItemWithMaster = Awaited<ReturnType<typeof getLostItemsWithMaster>>[number]
```

### 1-2. Server Actionの引数・戻り値の型

- フォームから送信される `FormData` は、Server Action内で必要な値を `formData.get('項目名')` として取り出し、必要に応じて型変換する(数値は `Number()`、日時は `new Date()`)
- Server Actionの戻り値(バリデーションエラーなど、画面に結果を戻す必要がある場合)は、以下の形の型に統一する

```typescript
type ActionResult =
  | { success: true }
  | { success: false; errors: Record<string, string> }
```

### 1-3. Client Componentのprops型

- Client Componentに渡すpropsは、コンポーネントファイル内で `type Props = { ... }` として定義する
- マスタデータ(カテゴリ・色・場所)をプルダウン用に渡す場合は、Prismaの型をそのまま使う(`Category[]` など)

## 2. コンポーネント構成の方針

### 2-1. ディレクトリ構成

```
src/
├── app/
│   ├── lost-items/
│   │   ├── page.tsx          # 一覧画面
│   │   ├── new/page.tsx      # 登録画面
│   │   └── [id]/
│   │       ├── page.tsx      # 詳細画面
│   │       └── edit/page.tsx # 編集画面
│   ├── found-items/          # lost-itemsと同様の構成
│   └── admin/                # 施設管理者向け画面
├── components/
│   ├── ui/                   # 汎用UIパーツ(ボタン、フォーム部品など)
│   └── features/             # 機能ごとのコンポーネント(例: LostItemCard)
└── lib/
    ├── prisma.ts             # PrismaClientのシングルトン
    └── actions/               # Server Actionをまとめる場所(例: lost-items.ts)
```

### 2-2. Server Component / Client Componentの使い分け

- **デフォルトはServer Component**とする(`"use client"` を書かない)
- 以下のいずれかに該当する場合のみ Client Component にする
  - `onClick` などのイベントハンドラが必要
  - `useState` / `useEffect` などのReact Hooksが必要
  - ブラウザAPI(`window` など)を直接使う必要がある
- フォームの入力欄自体はServer Componentのままでよい(`<form action={serverAction}>` を使えば、JS無効環境でも動作する)。入力値のリアルタイムバリデーションなど、動的な見た目の変化が必要な部分だけをClient Componentに切り出す

### 2-3. 共通コンポーネントの粒度

- `components/ui/`: ボタン、入力欄、セレクトボックスなど、アプリ固有のロジックを持たない見た目だけの部品
- `components/features/`: 「落とし物カード」「マッチング候補一覧」など、特定の機能に紐づくコンポーネント

## 3. state設計の方針

### 3-1. 基本方針

- Server Component中心の構成のため、**クライアント側のstate(`useState`)は最小限に留める**
- フォームの送信・登録処理は、`useState` でのフォーム管理ではなく、**Server Actionへの `<form action={...}>` 送信**を基本形とする

### 3-2. `useState` を使うケース(例外)

- モーダル・ドロップダウンなどのUIの開閉状態
- 検索・絞り込みフォームの入力途中の値(送信前の一時保持)
- マッチング候補一覧で「詳細を開く/閉じる」のような、DBに保存しない一時的な表示切り替え

### 3-3. サーバー側の状態管理

- 落とし物・拾得物の `status`(未マッチング/確認中/返却済み)、`matches` の確定記録など、**アプリの本質的な状態はすべてDBで管理する**。クライアント側のstateに「正」のデータを持たせない

## 4. バリデーション設計の方針

### 4-1. 基本方針

- バリデーションは **Server Action内(サーバー側)で必ず行う**。クライアント側の入力チェック(`required` 属性など)は補助的なものとし、サーバー側のチェックを省略しない
- 文字数制限は、`schema.prisma` で定義した `@db.VarChar(n)` の上限に合わせる

### 4-2. 主な項目のバリデーションルール

| 項目 | ルール |
|---|---|
| `email` | 必須、メールアドレス形式、最大255文字、重複不可 |
| `password` | 必須、最小8文字程度(ハッシュ化前の平文の入力値に対して) |
| `categoryId` / `colorId` / `locationId` | 必須、マスタに存在するIDであること |
| `secretInfo` | 必須、最大200文字 |
| `lostAt` / `foundAt` | 必須、未来日時は不可 |
| `locationDetail` | 任意、最大100文字 |

### 4-3. エラーの表示方法

- Server Actionでバリデーションエラーが発生した場合、`ActionResult`(1-2節参照)の `errors` に項目名をキーとしたエラーメッセージを入れて画面に戻す
- 画面側では、各入力欄の下にエラーメッセージを表示する
