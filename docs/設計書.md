# 設計書

落とし物管理・マッチングアプリのフロントエンド実装における、型定義・コンポーネント構成・state設計・バリデーション設計・認証設計の方針をまとめたもの。個別の画面を実装する際は、本書の方針に沿って設計する。

## 1. 型定義の方針

### 1-1. 基本方針

- DBのテーブル構造に対応する型は、独自に定義せず**Prismaが自動生成する型をそのまま利用する**
- `@/generated/prisma/client` からimportして使う

```typescript
import type { LostItem, FoundItem, Category, Color, Location, Facility, User, Match } from '@/generated/prisma/client'
```

- リレーション先を含めて取得したデータの型は、Prismaの `Prisma.LostItemGetPayload<...>` を使うか、関数の戻り値から `Awaited<ReturnType<typeof ...>>` で推論する。独自にリレーション込みの型を手書きしない(スキーマ変更時に型がズレる原因になるため)

```typescript
// 例: カテゴリ・色・場所を含めて取得する関数の戻り値型
async function getLostItemsWithMaster() {
  return prisma.lostItem.findMany({
    include: { category: true, color: true, location: true },
  })
}
type LostItemWithMaster = Awaited<ReturnType<typeof getLostItemsWithMaster>>[number]
```

### 1-2. Server Actionの引数・戻り値の型

- フォームから送信される `FormData` は、Server Action内で必要な値を `formData.get('項目名')` として取り出し、必要に応じて型変換する(数値は `Number()`、日時は `new Date()`)
- 画面にエラーメッセージを戻す必要があるServer Action(会員登録・ログインなど)は、`useActionState` と組み合わせて使うため、以下の形の状態型を定義する

```typescript
export type RegisterState = { error?: string } | undefined

export async function register(
  prevState: RegisterState,
  formData: FormData
): Promise<RegisterState> {
  // ...バリデーション・登録処理
  // エラー時: return { error: 'メッセージ' }
  // 成功時: redirect(...)
}
```

- エラー時に画面遷移を伴わない単純な処理(施設紐付けなど)は、`throw new Error(...)` で止め、Next.js標準のエラー画面に委ねる場合もある(実装コストとのバランスで使い分ける)

### 1-3. Client Componentのprops型

- Client Componentに渡すpropsは、コンポーネントファイル内で `type Props = { ... }` として定義する
- マスタデータ(カテゴリ・色・場所・施設)をプルダウン用に渡す場合は、Prismaの型をそのまま使う(`Category[]` など)

## 2. コンポーネント構成の方針

### 2-2. Server Component / Client Componentの使い分け

- **デフォルトはServer Component**とする(`"use client"` を書かない)
- 以下のいずれかに該当する場合のみ Client Component にする
  - `useActionState` など、Server Actionの結果を画面に反映するReact Hooksが必要(会員登録・ログインフォーム)
  - `onClick` などのイベントハンドラ、`useState` によるUI状態の切り替えが必要(パスワードの表示/非表示切り替えなど)
- フォームの入力欄自体はServer Componentのままでよい(`<form action={serverAction}>` を使えば、JS無効環境でも動作する)。エラーメッセージを画面上に自然な形で表示したい画面だけ、Client Componentに切り出す
- `'use client'` を使うコンポーネントと `'use server'` を使うServer Actionは、同じファイルに同居できない(Next.jsの制約)ため、フォームUIとServer Actionは必ず別ファイルに分割する

### 2-3. 認証状態の取得

- Server Component(`page.tsx`、`Header.tsx`など)では、`getCurrentUser()`(`src/lib/session.ts`)を直接 `await` して、ログイン中のユーザー情報を取得する
- ページ全体をログイン必須にしたい場合は、コンポーネント冒頭で取得し、`null` であれば `redirect('/login')` する
- Server Action内でも、実行のたびに `getCurrentUser()` を呼び直して権限を確認する(画面表示の出し分けとは別に、処理の実行可否を必ずサーバー側でも検証する)

## 3. state設計の方針

### 3-1. 基本方針

- Server Component中心の構成のため、**クライアント側のstate(`useState`)は最小限に留める**
- フォームの送信・登録処理は、`useState` でのフォーム管理ではなく、**Server Actionへの `<form action={...}>` 送信**を基本形とする
- 画面にエラーメッセージを表示する必要があるフォーム(会員登録・ログイン)は、`useActionState(action, undefined)` を用い、戻り値の `state.error` をそのまま表示する

### 3-2. `useState` を使うケース(実装した例)

- パスワード入力欄の表示/非表示切り替え(`showPassword`)
- 会員登録フォームで、管理者コードが入力されたかどうかによって、所属施設の選択欄を出し分ける(`isAdmin`)
- モーダル・ドロップダウンなど、今後追加され得るUIの開閉状態

### 3-3. サーバー側の状態管理

- 落とし物・拾得物の `status`(未マッチング/返却済み)、`matches` の確定記録、ログインセッションなど、**アプリの本質的な状態はすべてDB・Cookieで管理する**。クライアント側のstateに「正」のデータを持たせない
- マッチング候補とその一致度スコアは、DBに保存せず、詳細画面を開くたびにサーバー側(`calculateMatchScore`)で再計算する

## 4. バリデーション設計の方針

### 4-1. 基本方針

- バリデーションは **Server Action内(サーバー側)で必ず行う**。クライアント側の入力チェック(`required`・`max`属性など)は補助的なものとし、サーバー側のチェックを省略しない
- 文字数制限は、`schema.prisma` で定義した `@db.VarChar(n)` の上限に合わせる
- 日時系の入力は、フロント側で `<input type="datetime-local" max={...}>` により未来日時を選びにくくしつつ、サーバー側でも `Date.now()` と比較して最終チェックする。タイムゾーンの解釈ズレを防ぐため、フォームの値をDateに変換する際は日本時間のオフセット(`+09:00`)を明示する

### 4-2. 主な項目のバリデーションルール(実装済み)

| 項目 | ルール |
|---|---|
| `email` | 必須、メールアドレス形式、最大255文字、重複不可(Prismaの`P2002`エラーを検知してメッセージ化) |
| `password` | 必須、最小8文字(ハッシュ化前の平文の入力値に対して) |
| `name` | 必須 |
| `adminCode` | 任意。入力されているのに環境変数`ADMIN_CODE`と一致しない場合はエラー(登録自体をブロックする) |
| `facilityId`(管理者登録時) | 管理者コードが正しい場合のみ必須 |
| `categoryId` / `colorId` / `locationId` | 必須、マスタに存在するIDであること |
| `secretInfo` | 必須、最大200文字 |
| `lostAt` / `foundAt` | 必須、未来日時は不可(フロント`max`属性+サーバー側`Date.now()`比較の二重チェック) |
| `locationDetail` | 任意、最大100文字 |

### 4-3. エラーの表示方法

- `useActionState` を使う画面(会員登録・ログイン)では、Server Actionの戻り値(`{ error?: string }`)をそのままフォーム上部に赤字で表示する
- それ以外の画面では、`throw new Error(...)` によりNext.js標準のエラー画面で通知する(実装コストとのバランスを見て、今後 `useActionState` 化することも検討する)

## 5. 認証・認可設計の方針

### 5-1. 認証(誰か、を確認する)

- パスワードは `bcryptjs` の `bcrypt.hash(password, 10)` でハッシュ化して保存し、ログイン時は `bcrypt.compare` で照合する
- ログインセッションはJWTではなく、`userId` にHMAC-SHA256で署名を付けた文字列を、`httpOnly` のCookieに保存するシンプルな自作方式とした。署名の秘密鍵は環境変数 `AUTH_SECRET` で管理する
- ログイン中のユーザーが誰かは `getCurrentUser()` で取得する(Cookieの署名を検証し、正しければ該当ユーザーをDBから取得)

### 5-2. 認可(何ができるか、を確認する)

- 会員登録時に管理者コード(`ADMIN_CODE`)が正しく入力された場合のみ `role: 'ADMIN'` として登録され、所属施設の選択が必須になる
- 画面の表示制御: `currentUser?.role === 'ADMIN'` の判定で、管理者専用の操作(施設紐付けフォーム、返却確定ボタン、秘密情報の表示)や、一般ユーザー専用の操作(各種登録ボタン)を出し分ける
- 処理の実行制御: `assignFacility` ・ `confirmReturn` などのServer Action内でも、`getCurrentUser()` を呼び直し、管理者でなければ処理を拒否する(画面表示のみに頼らない二重防御)
- データの絞り込み: 落とし物一覧・詳細は、一般ユーザーには本人が登録したものだけを取得する(`where: { userId: currentUser.id }`)。管理者は全件取得する。拾得物は、落とし主が候補を見つけられる必要があるため一般ユーザーにも全件表示する
- 現時点でのスコープ外: URLを直接指定した場合の詳細ページへのアクセス制御(認可)までは未対応。一覧画面・導線の出し分けまでが対応範囲
