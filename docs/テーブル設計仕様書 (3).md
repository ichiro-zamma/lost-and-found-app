# テーブル設計仕様書

落とし物管理・マッチングアプリ(MVP)のためのテーブル設計。利用者、施設、場所、色、カテゴリ、落とし物、拾得物、マッチング結果を管理する8テーブル構成とした。

| No | テーブル物理名 | 論理名 | 概要 |
|----|--------------|--------|------|
| 1 | users | 利用者 | アプリを利用するユーザー(落とした人/拾った人/管理者) |
| 2 | facilities | 施設 | 拾得物を保管する拠点(駅の忘れ物センター、学校など) |
| 3 | locations | 場所 | 落とし物・拾得物が発生した場所のシチュエーション大枠(駅構内、電車内、公園内など) |
| 4 | colors | 色 | 落とし物・拾得物の色の選択肢(黒、白、赤など) |
| 5 | categories | カテゴリ | 落とし物・拾得物の種類の分類 |
| 6 | lost_items | 落とし物 | 落とした人が登録する落とし物情報 |
| 7 | found_items | 拾得物 | 拾った人が登録する拾得物情報 |
| 8 | matches | マッチング結果 | 対面での本人確認を経て確定した落とし物と拾得物の組み合わせの記録 |

## 1. users(利用者)

| カラム物理名 | データ型 | 制約 | 論理名 | 説明 |
|------------|---------|------|--------|------|
| user_id | SERIAL | PRIMARY KEY | 利用者ID | 自動採番 |
| name | VARCHAR(50) | NOT NULL | 氏名　| 
| email | VARCHAR(255) | NOT NULL, UNIQUE | メールアドレス | ログインID兼用 |
| password | VARCHAR(255) | NOT NULL | パスワード| 平文保存禁止 |
| role | Role (Prismaではenum) | NOT NULL, DEFAULT 'USER' | 権限区分 | USER=一般ユーザー(落とした人/拾った人兼用) / ADMIN=施設管理者。DBのENUM型で値を制限する |
| facility_id | INTEGER | FK → facilities.facility_id | 所属施設ID | role='ADMIN'の管理者のみ設定。一般ユーザーはNULL |
| created_at | TIMESTAMP | NOT NULL, DEFAULT now() | 登録日時 | |

```sql
CREATE TABLE users (
    user_id       SERIAL PRIMARY KEY,
    name          VARCHAR(50),
    email         VARCHAR(255) NOT NULL UNIQUE,
    password VARCHAR(255) NOT NULL,
    role Role NOT NULL DEFAULT 'USER',
    facility_id   INTEGER REFERENCES facilities(facility_id),
    created_at    TIMESTAMP NOT NULL DEFAULT now()
);
```

## 3. locations(場所)

| カラム物理名 | データ型 | 制約 | 論理名 | 説明 |
|------------|---------|------|--------|------|
| location_id | SERIAL | PRIMARY KEY | 場所ID | 自動採番 |
| location_name | VARCHAR(50) | NOT NULL, UNIQUE | 場所名 | 例: 駅構内、電車内、公園内、学校内、飲食店内など、シチュエーションの大枠。個別の駅名・施設名は含めず、選択肢の数を抑える。具体的な場所は`location_detail`(自由記述)で補う |

```sql
CREATE TABLE locations (
    location_id   SERIAL PRIMARY KEY,
    location_name VARCHAR(50) NOT NULL UNIQUE
);
```

facilities(拾得物を「保管」している場所)とは別概念。locationsは落とし物・拾得物が「発生した」場所を表す。

## 6. lost_items(落とし物)

| カラム物理名 | データ型 | 制約 | 論理名 | 説明 |
|------------|---------|------|--------|------|
| lost_item_id | SERIAL | PRIMARY KEY | 落とし物ID | 自動採番 |
| user_id | INTEGER | NOT NULL, FK → users.user_id | 登録者ID | 落とした人 |
| category_id | INTEGER | NOT NULL, FK → categories.category_id | カテゴリID | 種類の一致判定に使用 |
| color_id | INTEGER | NOT NULL, FK → colors.color_id | 色ID | 選択式(不明・その他を含む)。色の一致判定に使用(完全一致で判定できる) |
| location_id | INTEGER | NOT NULL, FK → locations.location_id | 紛失場所ID(大枠) | 選択式。完全一致で+15点 |
| location_detail | VARCHAR(100) | | 紛失場所の詳細(自由記述) | 例:「渋谷駅の改札口付近」。曖昧検索で+15点(任意項目) |
| lost_at | TIMESTAMP | NOT NULL | 紛失日時 | 一致度スコアの加点対象(近さで判定) |
| secret_info | VARCHAR(200) | NOT NULL | 本人確認用秘密情報 | 例:「財布の中に○○が入っている」。拾得者には非公開 |
| status | ItemStatus (Prismaではenum) | NOT NULL, DEFAULT 'UNMATCHED' | ステータス | UNMATCHED=未マッチング/ RETURNED=返却済み。PrismaではItemStatus enumで表現 |
| created_at | TIMESTAMP | NOT NULL, DEFAULT now() | 登録日時 | |

```sql
CREATE TABLE lost_items (
    lost_item_id SERIAL PRIMARY KEY,
    user_id      INTEGER NOT NULL REFERENCES users(user_id),
    category_id  INTEGER NOT NULL REFERENCES categories(category_id),
    color_id     INTEGER NOT NULL REFERENCES colors(color_id),
    location_id  INTEGER NOT NULL REFERENCES locations(location_id),
    location_detail VARCHAR(100),
    lost_at      TIMESTAMP NOT NULL,
    secret_info  VARCHAR(200) NOT NULL,
    status       ItemStatus NOT NULL DEFAULT 'UNMATCHED',
    created_at   TIMESTAMP NOT NULL DEFAULT now()
);
```

## 7. found_items(拾得物)

| カラム物理名 | データ型 | 制約 | 論理名 | 説明 |
|------------|---------|------|--------|------|
| found_item_id | SERIAL | PRIMARY KEY | 拾得物ID | 自動採番 |
| user_id | INTEGER | NOT NULL, FK → users.user_id | 登録者ID | 拾った人(一般ユーザーが直接登録) |
| category_id | INTEGER | NOT NULL, FK → categories.category_id | カテゴリID | 種類の一致判定に使用 |
| color_id | INTEGER | NOT NULL, FK → colors.color_id | 色ID | 選択式(不明・その他を含む)。色の一致判定に使用(完全一致で判定できる) |
| location_id | INTEGER | NOT NULL, FK → locations.location_id | 拾得場所ID(大枠) | 選択式。完全一致で+15点 |
| location_detail | VARCHAR(100) | | 拾得場所の詳細(自由記述) | 例:「渋谷駅の改札口付近」。曖昧検索で+15点(任意項目) |
| found_at | TIMESTAMP | NOT NULL | 拾得日時 | 一致度スコアの加点対象(近さで判定) |
| facility_id | INTEGER | FK → facilities.facility_id | 保管施設ID | 登録時はNULL(未保管)。実物を施設に届けた後、管理者が設定 |
| status | ItemStatus (Prismaではenum) | NOT NULL, DEFAULT 'UNMATCHED' | ステータス | UNMATCHED=未マッチング / RETURNED=返却済み |
| created_at | TIMESTAMP | NOT NULL, DEFAULT now() | 登録日時 | |

```sql
CREATE TABLE found_items (
    found_item_id SERIAL PRIMARY KEY,
    user_id       INTEGER NOT NULL REFERENCES users(user_id),
    category_id   INTEGER NOT NULL REFERENCES categories(category_id),
    color_id      INTEGER NOT NULL REFERENCES colors(color_id),
    location_id   INTEGER NOT NULL REFERENCES locations(location_id),
    location_detail VARCHAR(100),
    found_at      TIMESTAMP NOT NULL,
    facility_id   INTEGER REFERENCES facilities(facility_id),
    status       ItemStatus NOT NULL DEFAULT 'UNMATCHED',
    created_at    TIMESTAMP NOT NULL DEFAULT now()
);
```

## 8. matches(確定した組み合わせの記録)

一致度スコアの計算(種類・色・場所・日時)自体は元データから都度再計算できるためDBには保存しない(React側の関数で計算し、候補一覧として表示するだけ)。このテーブルは「対面での本人確認を経て、実際に成立・返却した組み合わせ」だけを記録する、実績としての履歴テーブルである。

| カラム物理名 | データ型 | 制約 | 論理名 | 説明 |
|------------|---------|------|--------|------|
| match_id | SERIAL | PRIMARY KEY | マッチングID | 自動採番 |
| lost_item_id | INTEGER | NOT NULL, FK → lost_items.lost_item_id | 落とし物ID | |
| found_item_id | INTEGER | NOT NULL, FK → found_items.found_item_id | 拾得物ID | |
| matched_at | TIMESTAMP | NOT NULL, DEFAULT now() | 確定・返却日時 | 管理者が対面確認し、実物を手渡した日時 |
| — | — | UNIQUE (lost_item_id), UNIQUE (found_item_id) | — | 1つの落とし物・1つの拾得物がそれぞれ1件の確定組み合わせしか持てないよう、1対1の関係を保証 |

```sql
CREATE TABLE matches (
    match_id      SERIAL PRIMARY KEY,
    lost_item_id  INTEGER NOT NULL UNIQUE REFERENCES lost_items(lost_item_id),
    found_item_id INTEGER NOT NULL UNIQUE REFERENCES found_items(found_item_id),
    matched_at    TIMESTAMP NOT NULL DEFAULT now()
);
```

## テーブル間リレーション一覧

| 親テーブル | 子テーブル | カーディナリティ | 備考 |
|-----------|-----------|-----------------|------|
| facilities | users | 1 : 0以上 | 1つの施設に複数の管理者が所属し得る |
| facilities | found_items | 1 : 0以上 | 1つの施設が複数の拾得物を保管する |
| locations | lost_items | 1 : 多 | 1つの場所が複数の落とし物の発生場所として使われる |
| locations | found_items | 1 : 多 | 1つの場所が複数の拾得物の発生場所として使われる |
| colors | lost_items | 1 : 多 | 1つの色が複数の落とし物に使われる |
| colors | found_items | 1 : 多 | 1つの色が複数の拾得物に使われる |
| users | lost_items | 1 : 0以上 | 1人の利用者が複数の落とし物を登録する |
| users | found_items | 1 : 0以上 | 1人の利用者が複数の拾得物を登録する |
| categories | lost_items | 1 : 多 | 1つのカテゴリが複数の落とし物に使われる |
| categories | found_items | 1 : 多 | 1つのカテゴリが複数の拾得物に使われる |
| lost_items | matches | 1 : 0または1 | 1つの落とし物は、確定した拾得物との組み合わせを最大1件しか持たない(1対1) |
| found_items | matches | 1 : 0または1 | 1つの拾得物は、確定した落とし物との組み合わせを最大1件しか持たない(1対1) |

## マッチング候補のスコア計算(Reactで都度計算、DB保存なし)

一致度スコアは`lost_items`と`found_items`のデータから、フロントエンド(Reactの関数)でその場で計算し、候補一覧として表示する。計算結果自体はDBに保存しない(元データがあればいつでも再計算できるため)。

- **種類・色**: マスタテーブル(categories / colors)のIDによる完全一致判定
- **場所(大枠)**: `locations`マスタのIDによる完全一致判定(+15点)
- **場所(詳細)**: `location_detail`同士の曖昧検索(部分一致)による判定(+15点)。`location_id`で大枠が一致していることが前提のため、無関係な場所同士が誤って一致するリスクは小さい
- **日時近接**: `lost_at`と`found_at`の差が一定期間(例: ±3日)以内かどうかで判定

## セキュリティ上のルール(アプリケーション側で実装)

- `found_items.facility_id`は、拾得物登録時点ではNULLでもマッチング候補としては表示される。管理者が実物確認後に`facility_id`を設定すると、候補に施設名・住所が追加表示される(施設情報自体を意図的に隠す仕組みは設けない)。
- 本人確認は、施設管理者が`lost_items.secret_info`と実物を対面で照合して行う。落とし主やシステムによる自動照合は行わない。確認が取れたら`matches`に確定した組み合わせを記録し、`lost_items.status`/`found_items.status`を`'RETURNED'`(返却済み)に更新する。
- ステータスを`'RETURNED'`(返却済み)に更新し、`matches`にレコードを作成できるのは、施設管理者(role='ADMIN')のみとする。落とし主による自己申告での更新は許可しない(実際に受け取っていないのに更新されるリスクを防ぐため)。

## MVP範囲外(拡張候補)としたテーブル

- `messages` — 落とした人と拾った人のメッセージ機能を追加する場合
- `returns` — 返却履歴(いつ・どの管理者が対応したか)を別テーブルとして記録したい場合。現状は各itemの`status='RETURNED'`で代替
